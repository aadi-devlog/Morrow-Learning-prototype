# Morrow Learning: enquiry and lead-capture implementation plan

**Status:** Production recommendation. The current website form is a front-end demonstration; no enquiry is transmitted or stored.

## 1. Conversion journey

1. A visitor selects **Talk to our team**, **Enquire now** or a programme-specific enquiry CTA.
2. The selected programme is prefilled when the visitor starts from a programme card.
3. The visitor provides name, email, programme interest and explicit contact consent. Keep optional questions short; avoid collecting sensitive information.
4. The form validates required fields in the browser and submits securely to an approved backend endpoint.
5. The backend validates again, applies spam/rate controls, creates a lead record and returns a reference number.
6. The visitor sees a clear confirmation and receives an acknowledgement email. The organisation's admissions owner receives a notification.
7. An assigned team member follows up within a founder-approved service window, records outcome and updates the lead status.

## 2. Suggested lead record

| Field | Purpose | Handling |
|---|---|---|
| Lead ID | Unique reference | Generated by backend |
| Created timestamp | Track response time | Generated by backend |
| Name and email | Reply to the enquiry | Required; access restricted |
| Programme interest | Route to the right programme owner | Required or “Not sure yet” |
| Source/CTA | Understand which page or button converted | Store non-sensitive campaign metadata |
| Consent text/version/time | Evidence of the contact permission | Store the exact notice version and timestamp |
| Status and owner | Track follow-up | New, contacted, qualified, enrolled, not proceeding |
| Notes / next action | Keep follow-up accountable | Limit to necessary, professional notes |

Do not collect phone numbers, college, budget or career details unless the admissions process has a clear reason and a privacy notice explaining the use.

## 3. Low-code integration option

**Simple MVP:** Website form -> secure form endpoint (or approved form service) -> Google Sheets/CRM -> email acknowledgement + internal notification.

**Suggested automation:** Make or n8n can listen for a new accepted lead, create/update a CRM record, notify the assigned owner and send an acknowledgement. Use an idempotency key or lead ID to prevent duplicate records. Do not expose CRM credentials or API keys in front-end JavaScript.

A direct backend-to-CRM integration is preferable when the organisation has a supported CRM. If a spreadsheet is used for a small pilot, restrict access, enable audit history and define retention/deletion rules.

## 4. Privacy, security and operational controls

- Publish the organisation's approved identity, privacy notice, contact purpose and retention period before enabling a live form.
- Use HTTPS, server-side validation, anti-spam/rate limiting and secure credential storage.
- Collect only information needed to respond; do not put personal form fields into analytics events.
- Separate marketing consent from a one-time response to an enquiry if ongoing marketing messages are planned.
- Provide a way for the user to request correction/deletion where applicable.
- Limit staff access and define who owns follow-up and data cleanup.
- Test success, invalid input, duplicate submission, network failure and email-delivery failure before launch.

## 5. Recommended CTA hierarchy

- Primary: **Enquire about this programme** (programme-specific and preselected).
- Secondary: **Talk to our team** (general enquiry).
- Supporting: **Explore programmes** and **See project examples** (help undecided visitors learn before submitting).

Avoid unsupported claims about job placement, accreditation, instructor experience, cohort dates, certificate value or guaranteed outcomes. The prototype appropriately leaves these details for founder approval.

## 6. Pilot funnel metrics

Track visits to programme sections, CTA clicks, form starts, successful submissions, qualified leads, response time and enrolments. Use a consistent definition for each metric and a baseline before setting targets. Do not treat CTA clicks as leads or form submissions as paid enrolments.

## 7. Founder decisions required before launch

Confirm the legal/operating brand, programme facts, approved contact channels, privacy notice, admissions owner, service-level target, CRM/form provider, retention policy and whether marketing follow-up is permitted.

---

**Implementation boundary:** The supplied HTML validates a local demo form and shows an explanatory success state. It does not send or save personal information and must not be presented as a live admissions form.
